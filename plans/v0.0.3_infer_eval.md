# RMT v0.0.3：编译推理与可复现评测

日期：2026-09-29。前置：[v0.0.2 计划](v0.0.2_bound_rmt_bootstrap.md)、[实施记录](v0.0.2_bound_rmt_bootstrap_record.md)。

本文是实施计划，不代表下面的优化、评测和依赖组合已运行通过。用户已授权开始实施和验证；过程见 [实施记录](v0.0.3_infer_eval_record.md)。

## 1. 目标与已确认决策

交付可用于后续训练迭代的 RMT 推理入口、Qwen 对照入口，以及基于现有评测工具的统一评测流程。

| 项目 | 决策 |
| --- | --- |
| 模型 | 本地 Qwen3-4B 与 HF 格式 RMT；纯文本；默认 E=R=36 |
| RMT 推理 | 默认启用真实 `torch.compile`，默认启用按固定循环深度组织的 KV cache |
| Qwen 推理 | 优先 vLLM；兼容性或接入成本不合适时退回 Transformers |
| 评测工具 | 优先 EvalScope；已有 scorer／数据 adapter／沙箱优先复用 |
| 首轮模式 | **用户已确认：先 non-thinking 完成代表性评测，再扩展 thinking** |
| 性能决策顺序 | **用户已确认：先测 compile 相对 eager 的加速、吞吐和显存，再决定完整评测规模** |
| GPU | 用户最新授权允许物理 GPU 0–7 |
| 数值要求 | **用户已确认：保留 bitwise 严格参考路径；默认编译性能路径单独验收误差和质量** |

模型来源：

- Qwen：`/share/project/eai_pwm/models/Qwen/Qwen3-4B`。
- 等价 RMT：`artifacts/bootstrap/rmt-bound-4b`，默认 `layer_order`。
- 学习路由：接收任意明确指定的 RMT HF checkpoint；v0.0.2 训练恢复文件是 DCP，不能冒充 HF checkpoint 直接加载。没有合适的已训练 HF 权重时，用受控 forced／learned 路由作性能与语义测试，并标明权重来源；不把压力测试模型当质量候选。

本版扩展并验证 KV cache，固定循环数下每个 recurrence 独立保存历史 K/V，专家切换不能重写历史状态。默认 cached prefill/decode，无 cache 路径仅作参考。动态退出、解除绑定和训练不在范围内。

## 2. 现状与性能问题

v0.0.2 已有 HF 导出、batch generation、QKV／O／FFN 投影编译接口和小模型组合验证，但还没有真实 4B 编译推理的系统验收。

目前 `experts.py` 的混合路由按专家调用 `nonzero`、gather／scatter 和 Python 循环；`attention.py` 构造平方大小的显式 mask，并展开 GQA 的 K/V heads。生成默认配置还可能开启 cache。这些行为都必须在新推理入口中明确处理。

采用一次 prefill 后逐 token decode，避免全前缀重算。先保留 DynamicCache 作为数值参考，再验证预分配容量的 cache，使 decode 的 cache 写入和编译形状稳定；维护有效长度、padding 和 batch 行映射。

## 3. 推理架构

### 3.1 独立环境与接口

保留当前模型环境 Python 3.13.14／torch 2.10.0+cu130／Transformers 4.57.6 作为起点。EvalScope 和 vLLM 使用独立环境，分别锁版本、wheel 来源和依赖清单，避免安装 vLLM 时替换已验证的模型 torch。

优先采用本机 HTTP 解耦：

```text
EvalScope（任务、数据、评分、结果恢复）
  ├─ RMT 本地接口 → 请求队列／微批处理 → compiled RMT，recurrence KV cache
  └─ Qwen 本地接口 → vLLM；失败时使用 Transformers 适配器
```

RMT 同时提供离线批量推理入口，便于没有 HTTP 开销的性能测量与定位。HTTP 只实现首轮所需的 chat／文本 completion、模型信息、健康检查、usage、finish_reason 和错误结构；不为了兼容名称而假装支持尚未实现的 tools／logprobs／streaming。

EvalScope 的 OpenAI-compatible 接口优先复用；若所选 adapter 必须获得额外输出，则只增加薄层 `ModelAPI` 适配，不重写评测框架。[EvalScope 接口依据][eval-custom]

### 3.2 RMT 批量生成

- 从 HF config 和权重读取循环数、专家数、路由模式和先验；推理不改变或衰减先验。
- `eval()`＋`inference_mode()`＋BF16，关闭 hidden／router 全量返回和训练专用 loss 路径；诊断 trace 按需开启。
- cached prefill/decode；常规生成只计算每行最后一个有效位置的 LM head，避免物化 `[B,S,V]` logits。严格诊断入口可另算完整 logits。
- 实现按 prompt 长度分桶的静态 batch／微批队列，多卡采用单卡模型副本分发任务，首先不引入 tensor parallel。所有模型副本仅绑定授权卡。
- 每个请求保留稳定 sample ID、生成计数、RNG、stop 状态和原始顺序；EOS／stop 后结束该请求，按明确策略压缩或补空 batch，不让结束行污染统计或改变其它请求的采样序列。
- 处理左右 padding、position IDs、padding query 和全 mask 行；bucket 内有冗余空间时不能把最后一个 padding 位置当作 next-token 位置。
- chat template 只应用一次；显式传入 `enable_thinking`。保留渲染后的 prompt／token ID 指纹，确保 Qwen 和 RMT 真正收到同一输入。
- 支持 temperature、top-p、top-k、presence penalty、seed、max_new_tokens、EOS 和 stop strings。presence penalty 不能偷换成 repetition penalty；明确其作用范围并与 Qwen 后端对照。
- 超长输入显式报错或进入配置允许的长度桶；不能静默裁切题目。OOM 可按确定规则减小 batch 重试，保持 sample ID／seed，并记录失败和重试。

### 3.3 编译与算子优化路线

必须使用 Inductor 等真实编译后端；不使用 `backend='eager'` 作为成功验收，不允许生产配置在编译失败后静默全量回退 eager。

1. **建立同条件基准**：RMT eager、现有投影 compile，保持其它开关相同，先测真实 4B。
2. **固定路径**：尝试捕获单 cell／多个循环的计算，输入按 shape bucket 组织；用编译时间、图大小和热运行时间决定边界。不要默认把 36 次循环全部展开成一个巨图。
3. **混合路径**：保留正确性参考 dispatch，定位 GPU→CPU 同步、逐专家小 GEMM 和临时张量；优先减少重复分组、分配与 Python 开销。空专家跳过不能改变 token 顺序或 attention 可见性。
4. 若投影编译无法带来有效收益，继续比较排序后分段 dispatch、固定容量的分组表示或成熟 grouped GEMM；必须无 token 丢弃，禁止物化逐 token 权重副本。自定义 kernel 不作为默认第一步。
5. 评估 SDPA／融合 attention 与原生 GQA 支持，实际记录选中的 kernel；不能因为调用了 SDPA 就声称使用 FlashAttention。无 padding 的方形全前缀可考虑 causal fast path；有 padding 必须使用正确 mask 或分桶方案，不能直接省略 mask。
6. 比较动态长度与有限 shape buckets。输出长度逐步增加不应导致每个 token 都编译一个新图；记录 guard failure、重编译数、缓存命中和 eager 区域。

编译缓存 key 至少包含实现／依赖版本、设备、dtype、E/R、路由模式、attention backend 和 shape 策略；权重是否能安全复用图按实际图捕获方式检查。禁止复用含旧参数常量的图。

### 3.4 原生 Qwen 对照

vLLM 原生支持 `Qwen3ForCausalLM`，但本机安装与运行组合仍需实测。[vLLM 支持表][vllm-models]

- 首先单卡加载本地 BF16 权重并完成 tokenizer、non-thinking 和样例生成检查；基线允许使用 vLLM 的 KV cache。
- 原生 Qwen vLLM 与 RMT compiled/cached 的端到端结果是“不同服务实现”的比较，不能据此归因模型结构速度优劣。
- 另保留 Transformers Qwen eager/no-cache，作为与 RMT 严格参考路径匹配的数值对照；需要归因 compile 收益时仅比较同一个 RMT、同 cache 策略。
- vLLM 经过一次锁定版本安装与启动排障仍无法适配时，记录原因并切换 Transformers，继续完成评测链路；不给依赖排障无限预算，也不破坏现有模型环境。

## 4. 性能测量与阶段决策

先测单卡，再测最多八卡独立副本的总吞吐。不同引擎尽量顺序运行，避免互相争用 GPU，冷启动和热运行分开报告。

建议初始矩阵：prompt 长度 128／512／2048，输出长度 32／128，batch 1／4／8；先运行小矩阵检查显存，必要时扩展到更长上下文。分别测 `layer_order` 和真实混合路由，不能只优化退化成原 Qwen 的固定路径。

报告包括：

- 冷启动／编译时间，首次响应时间，逐 token 延迟分布、端到端 p50/p95。
- generated tokens/s、requests/s、GPU-hours、峰值 allocated／reserved 显存。
- prefill／decode token 数和 cache 容量，另记录无 cache 对照的重算 token 数；不能将它当作对用户生成的 token 数抬高吞吐。
- 编译图数、热运行重编译、CPU 调度和 GPU kernel 时间、专家负载；编译范围外的开销占比。
- batch 内长度差异和 padding 浪费；对实际评测样例补测 EOS 正常结束的吞吐。

采用固定长度 synthetic 测速时明确 EOS 策略，不能用早停导致的 token 数差异制造加速。预热后至少重复三轮，CUDA 同步后计时，报告离散度。

**建议性能门槛，实施前冻结**：首轮代表性矩阵中 compile/eager 热吞吐几何平均 ≥1.10×，单项退化超过 10% 必须定位；动态混合路由单独报告。该数值是工程目标，不是已实现承诺。未达目标时继续优化并记录测得的约束，不能只以“成功编译”宣布性能完成，也不事后放宽门槛。

完成测速后，用真实评测 pilot 的输入／输出长度分布估算首轮 GPU-hours、墙钟时间和截断比例，自主采取保守预算确定正式样本量、输出上限及 thinking 扩展规模，并记录依据。

## 5. 数值一致性与优化验收

用户已确认：保留 `reference` 严格路径，默认正式推理使用 `compiled` 性能路径，二者分别验收。

- `reference`：原权重、`layer_order`、相同 eager 算子／dtype／mask／position IDs，继续验证与 HF Qwen 的严格一致性。新增逐字节比较有效 token 输出，不能仅凭最大差值为零泛化所有 bit pattern 或所有输入。
- `compiled`：不预先承诺 bitwise-identical。逐阶段对照 eager 的 hidden／logits／NLL，记录 top-1、greedy 序列和路由变化。初始固定路径建议保持 v0.0.2 的相对 RMSE≤1e-3、|ΔNLL|≤1e-3；融合 kernel 不通过时先定位或保留该部分 eager，不为了通过而放宽阈值。
- learned 路由的 argmax 临界点可能放大微小误差。先用固定 forced 路由对照隔离算子误差，再测 margin 充足的 learned 样例，最后单独报告临界路由样例。
- sampling 的同 seed 不能保证跨后端逐 token 一致。工程回归使用 greedy／逐步 logits；正式能力评测使用已冻结采样协议，保存请求级 seed 和原始输出。
- 检查未来 token 不影响过去、batch 同伴不污染输出、非 thinking 模板、EOS／stop、长度桶边界、空响应、服务重启和续跑去重。

默认 compiled 路径不承担与原 Qwen 逐位一致的要求；任何质量回退仍需定位，不能用“浮点误差正常”掩盖路由、mask 或生成协议错误。

## 6. 评测集合与协议

### 6.1 采用哪个报告口径

本地模型是 Qwen3-4B，首先对齐 Qwen3 报告的 **post-training** 评测及对应 4B 表格；不把 Base 模型的 few-shot 设置混进来。建立下表的完整 inventory，逐项登记 EvalScope adapter、版本、数据 snapshot、评分器与是否可运行；本版先执行用户确认的 non-thinking 代表性集合。[报告依据][qwen-report]

| 类别 | 报告内评测项 | 本版处理建议 |
| --- | --- | --- |
| 通用 | MMLU-Redux、GPQA-Diamond、C-Eval、LiveBench（2024-11-25） | Redux／C-Eval 首轮；其余登记版本与访问条件 |
| 指令／偏好／写作 | IFEval、Arena-Hard、AlignBench v1.1、Creative Writing v3、WritingBench | IFEval 首轮；judge 类待确认评分模型及费用 |
| 数学／推理 | MATH-500、AIME’24／’25、ZebraLogic、AutoLogi | MATH-500 首轮；其余分阶段扩展 |
| 工具／代码 | BFCL v3、LiveCodeBench v5、CodeForces／CodeElo | LCB 首轮；工具交互与竞技评分单独接入 |
| 多语言 | Multi-IF、INCLUDE、MMMLU、MT-AIME2024、PolyMath、MLogiQA | 建 inventory，语言／抽样比例逐项冻结后扩展 |
| 长上下文附录 | RULER | 先登记；不默认承诺长上下文全量运行 |

首轮建议集合：**MMLU-Redux、C-Eval、IFEval、MATH-500、LiveCodeBench v5**，覆盖知识、中文、指令、数学和代码。每集先取固定 16–32 个样例做链路 pilot；正式代表性规模在第 4 节测速后确定，尽可能对较小集合跑全量，对大集合按类别固定分层抽样。pilot 分数不能充当正式质量结论。

EvalScope 文档已列出多个对应 adapter，但“存在同名任务”不意味着与论文版本／prompt／评分协议相同，必须读锁定版本的实现核对。[支持目录][eval-datasets]

### 6.2 报告协议与快速回归协议分开保存

报告协议的关键参数需显式落盘：thinking 使用 T=0.6／top-p=0.95／top-k=20；non-thinking 使用 T=0.7／top-p=0.8／top-k=20／presence penalty=1.5。thinking 的写作任务另有 penalty 设置；输出上限一般 32,768，AIME 为 38,912。GPQA 每题 10 次、AIME 每题 64 次取平均准确率；不能把该平均值标为 pass@64。LCB v5 对应 2024.10–2025.02。[协议依据][qwen-report]

工程回归可使用 greedy、较少样例和较短输出，但命名为 `quick_non_thinking`，记录与报告的全部差异。短输出上限不能只作用于 RMT；参与质量对比的模型必须使用同一协议，记录 `finish_reason=length` 的比例。

`report_non_thinking`／`report_thinking` 则保留报告采样与长度要求。若资源不足、数据或 judge 不可得，标记具体项 `deferred`／`blocked`，不能悄悄缩短输出后声称复现报告。模型 max context 必须覆盖 prompt＋output；超出本地配置的扩展要单独验证，不自动打开 YaRN。

EvalScope 的 Qwen3 示例集合是工具使用示范，其任务选择、LCB 日期与输出上限不能直接当作论文复现配置。[示例依据][eval-qwen3]

### 6.3 复用与数据基础设施

- EvalScope 负责 dataset adapter、prompt、答案提取、评分、聚合和已有恢复能力；项目新增 backend adapter、协议配置和结果校验。
- 某任务缺失时先复用官方 runner 或成熟工具，将输出转换成其标准输入；确需自定义时只写最小胶水。不要重新实现数学等价判断、代码判题或指令评分。
- 代码评测优先使用工具现有沙箱：限制时间／内存／网络，隔离执行生成代码，记录 runner／镜像版本。
- GPQA 等访问受限数据按许可获取；没有凭据时登记阻塞，不用近似替代集冒充。judge 类任务待用户确定模型、端点和预算后执行。
- 下载后保存 dataset revision、split、样本 ID／hash、few-shot 内容、日期过滤、语言集合、抽样 seed 和 scorer 版本；固定 selection manifest，所有模型复用。
- 原始响应、提取答案、错误／超时、token 数和每题分数可追溯。保存模型权重指纹、代码 commit、路由模式／先验、template、依赖、生成参数和硬件元数据。
- 恢复与结果缓存 key 包含模型、协议、题目及 repetition ID。服务超时重试不重复计分；不同 checkpoint／模式不共享生成结果缓存。
- 逐 benchmark 报告成绩、有效样本数、截断／失败率和置信区间；对重复采样按题目聚类统计。不把不同指标随意平均成一个“综合提升”。

## 7. 网络与环境策略

仅在实施阶段需要下载时，先做有超时的小请求探针；根据结果比较直连、用户提供的认证代理、两个备用代理。备用地址的 HTTP／SOCKS 类型先确认或探测，不凭端口假定。

代理只通过进程环境或未入库的本地配置注入。文档、git、shell trace、异常日志均不保存用户名／密码或带认证的 URL；网络失败日志脱敏。切换直连时同时清理大小写 http(s)_proxy／all_proxy；本地服务和内网地址保留适当 NO_PROXY，避免评测请求走代理。

采用超时、有限重试、断点续传和校验和；成功后锁定依赖与数据缓存，支持离线复跑。版本选择以实际安装和探针结果为准，计划阶段不虚构已兼容的 EvalScope／vLLM 精确版本。
